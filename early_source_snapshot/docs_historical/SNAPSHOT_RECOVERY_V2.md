## Отдельная новая реконструкция SQL

Файл `supabase/migrations/20261115100000_profile_nutrition_goals_compatibility.sql` восстановлен по прежнему базовому CAS и сохранённому контракту, **не побайтово**: SHA-256 `c83217e019df96fa147726588d408e29229b81c1f99726f9a0ed8cc1c8ff7e23`, прежний проверенный SHA был `b8516aeb67c4e7fb2d2e3f20a2470b2fe9b84479177e07bf94a02be166759ac7`. Он не применён к Supabase. Реконструкция сохраняет возраст, флаги измерений и подтверждения неизменённых целей при записи старым клиентом, только если прежний снимок цели валиден; при несовпадении снимает подтверждение. Записи блокируются и обновляются через CAS, лимит проверяется до и после слияния. Новая модель дополнительно сверяет снимки при чтении, в том числе если writer явно передал флаг с устаревшим снимком.

- `checks/profile_goals_postgres_reconstruction_v2_initial.{json,log}`: **46/46** локальных синтетических проверок в PostgreSQL 17.11, отдельный Unix-сокет, без TCP. Включены новые индивидуальные проверки каждой из шести целей, повреждённых/неполных снимков, нулей, сломанного старого профиля, конкурентного CAS, RLS и неизменности строк/прав при установке SQL.
- `checks/profile_goals_postgrest_reconstruction_v2_initial.json`: **18/18** на временной базе, реальном локальном PostgREST 14.18 и одном Flutter `SmartRemote` с двумя искусственными устройствами. Временная база удалена; использовались случайные короткоживущие тестовые токены, в отчёт они не записаны. Служба локальной PostgreSQL остановлена.
- Оба прогона касаются только искусственных данных и локальной схемы. Проверены не реальный Supabase Auth/production, не архивный клиент как самостоятельная программа, не Android, не резервная копия пользователя и не безопасность нескольких старых вкладок. SQL не менять в production до отдельного release gate и сверки истории миграций.
