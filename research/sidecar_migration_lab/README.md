# Лаборатория отдельной копии IndexedDB — только синтетика

**Не релиз, не миграция, не восстановление реального дневника и не резервная копия.** Исследуется возможность прочитать *модельную* старую базу v1, не повышая её версию, и сложить неизменённые выбранные значения в отдельную тестовую базу. В приложении этот прототип не включён. У него нет функции активации, переключения, удаления базы или записи в источник; приложение не умеет открывать такую копию как свой дневник.

## Зачем и что это не решает

Повышение версии одной IndexedDB до v2 блокирует обычное открытие v1: ошибка `VersionError`. Отдельная база не требует менять версию **модельного** v1-источника, но сама по себе не запрещает старой вкладке продолжать писать. Проверка двух снимков сообщает только о равенстве в моменты двух последовательных чтений: она не является атомарной проверкой двух баз и не останавливает будущие записи. Она также может не увидеть уже произошедшие изменения `A → B → A`.

В эксперименте сырая копия переносит в том числе фиктивный приватный маркер. Следовательно, она **не является очищенным экспортом** и непригодна для реальных данных. Не подключайте прототип к `fitness_v2`, реальным профилям, аккаунтам или облаку. Риск отката текущего синтетического кандидата остаётся: он уже использует v2.

## Что именно проверяется

- Только имена со случайными суффиксами `fitness_lab_legacy_*`, `fitness_lab_sidecar_*` и отдельно названная синтетическая база `fitness_synthetic_candidate`. Код требует безопасный loopback; harness дополнительно требует сетевой namespace только с loopback и одноразовые браузерные профили.
- Схема проверяется до чтения. Открытие источника в неподходящей версии, отсутствие источника и неожиданная схема отклоняются без создания целевой базы. Источник читается одним readonly-транзакционным снимком; запись строк и служебного маркера staging выполняется одной транзакцией **другой** базы. Успех запроса сам по себе не считается коммитом.
- Поддержаны ограниченные искусственные ключи и типы значений: строки, числа, bool, null, небольшие массивы и `ArrayBuffer`. Неизвестные типы отклоняются. Хеш — проверка представления выбранных значений, не криптографическая подпись и не доказательство отсутствия записей. Лимиты экспериментальны; `getAll` загружает данные в память **до** проверки размера.
- В модельной v1-фикстуре проверяются открытое старое соединение, сохранность источника, точные синтетические значения и байты, коллизия двух staging-попыток, искусственный abort после успеха запроса, отказ перезаписи заполненной копии и обнаружение отдельных несоответствий. Затем воспроизводятся пропуск `A → B → A` и запись сторонней вкладки при удержании Web Lock.
- Отдельный прогон загружает точную маркированную сборку **синтетического кандидата**, создаёт выдуманные воду и еду через интерфейс и сравнивает их сырой снимок с отдельной копией. Старая v1-фикстура при этом не является точным архивным приложением +14. Копия приватного маркера, последующая запись приложения и сохраняющийся `VersionError` фиксируются явно.

## Прогоны и установленный предел

Расширенные изолированные прогоны в Chromium 141.0.7390.37 и Firefox 142.0.1 дали каждый **27 PASS и 5 RISK_REPRODUCED**, без FAIL. Полные отчёты с SHA исходников и сборки — `attempts/chromium_interleaving.json` и `attempts/firefox_interleaving.json`. Это 27 заданных условий, не полный регресс и не устранение пяти рисков.

Дополнительно к первоначальным опытам воспроизведены два порядка: конкурентная запись была поставлена в очередь во время чтения парного readonly-снимка, а также старая модельная вкладка записала данные **после успешного сравнения**, пока лабораторный Web Lock ещё удерживался. Во втором случае повторное сравнение уже показало расхождение. Два изменения с возвратом к исходному значению сравнение, наоборот, не заметило. Эти примеры не доказывают безопасность любого расписания.

Первые версии harness дали по 25 PASS/5 RISK (`attempts/chromium_initial.json`, `attempts/firefox_initial.json`); соответствующий исходник сохранён в предыдущем Git commit `aaf410f`. Прямой запуск без сетевой изоляции отказал до открытия браузера (`attempts/outside_network_namespace_refusal.txt`). Скрипт `verify_results.py` сверяет сохранённые отчёты с текущими SHA и обязательными условиями; 9 unit-тестов проверяют и ошибочные отчёты. Это проверка согласованности файлов, не доказательство факта запуска или безопасности миграции.

Проверены только названные синтетические значения и сценарии. Настоящие дневники, все типы Hive, Safari/iOS, Android, Auth, sync, несколько устройств, реальная квота, внезапное выключение и откат не проверялись. Перед любым настоящим обновлением потребуются отдельный проект безопасной миграции и независимая проверка всех блокеров.

## Воспроизведение в отдельной среде

Нужны Linux, `sudo -n`, `unshare`, `setpriv`, `ip`, Node 20, Playwright 1.56.0 и установленные Chromium и Firefox. Сначала соберите и маркируйте синтетический `candidate/build/web` по `candidate/CANDIDATE_SAFETY.md`; он не входит в архив исходников. Затем, после загрузки зависимостей **до** сетевой изоляции:

```sh
cd research/rebuild_github_lab
npm ci --ignore-scripts --no-audit --no-fund
export NODE_PATH="$PWD/node_modules"
export PLAYWRIGHT_BROWSERS_PATH=/абсолютный/путь/к/браузерам
npx --no-install playwright install chromium firefox
cd ../sidecar_migration_lab
bash run_isolated.sh chromium /абсолютный/новый/chromium.json
bash run_isolated.sh firefox /абсолютный/новый/firefox.json
```

Оба отчёта должны быть новыми файлами. Запуск за пределами отдельного loopback namespace отклоняется до запуска браузера; сам `127.0.0.1` не заменяет изоляцию сети. Браузеры и SDK не включены в репозиторий.
